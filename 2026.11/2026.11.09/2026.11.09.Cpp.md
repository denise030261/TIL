### 항목 26. 변수 정의는 늦출 수 있는 데까지 늦추는 근성을 발휘하자

변수를 정의하면 반드시 물게 되는 비용이 드는 경우

- 프로그램 제어 흐름이 변수의 정의에 닿을 때 생성자가 호출되는 비용

- 그 변수가 유효범위를 벗어날 때 소멸자가 호출되는 비용
  
  

위의 경우를 막기 위해서는 아래와 같은 경우를 생각해야 한다

- 어떤 변수를 사용해야 할 때가 오기 전까지 그 변수의 정의를 늦추는 것은 기본이고, 초기화 인자를 손에 넣기 전까지 정의를 늦출 수 있는지 확인한다

- 해야 쓰지도 않을 객체가 만들어졌다 없어지는 일이 생기지 않으며, 불필요한 기본 생성자 호출도 일어나지 않는다.
  
  

루프 안에 변수를 정의하는 방법은 아래와 같다

```
// A 방법 : 루프 바깥쪽에 정의
Widget w;
for(int i=0;i<n;i++)
{
	w=i에 따라 달라지는 값;
    ...
}

// B 방법 : 루프 안쪽에 정의
for(int i=0;i<n;++i)
{
	Widget w(i에 따라 달라지는 값);
    ...
}
```



대입이 생성, 소멸자 쌍보다 비용이 덜 들고 전체 코드에서 수행 성능에 민감한 부분을 건드리면 방법 A를 아니면 방법 B를 사용하면 된다.



### 항목 27: 캐스팅은 절약, 또 절약! 잊지 말자

C++ 동작 규칙은 어떤 일이 있어도 타입 에러가 생기지 않도록 보장한다

C스타일 캐스트(구형 스타일의 캐스트)는 아래와 같다

(T) 표현식 // 표현식 부분을 T 타입으로 캐스팅한다.
T (표현식) // 표현식 부분을 T 타입으로 캐스팅한다. 이 방법은 함수 방식 캐스팅



C++는 네 가지로 이루어진 새로운 형태의 캐스트 연산자를 독자적으로 제공한다

신형 스타일 캐스트 혹은 C++ 스타일의 캐스트라고 한다

- const_cast<T>(표현식)

- dynamic_cast<T>(표현식)

- reinterpret_cast<T>(표현식)

- static_cast<T>(표현식)
  
  

const_cast<T>

- 객체의 상수성(constness)을 없애는 용도로 사용된다

dynamic_cast

- '안전한 다운캐스팅(safe downcasting)'을 할 때 사용하는 연산자이다

- 주어진 객체가 어떤 클래스 상속 계통에 속한 특정 타입인지 아닌지를 결정하는 작업에 쓰인다. 

- 런타임 비용이 높은 캐스트 연산자로도 유일하다.

reinterpret_cast

- 포인터를 int로 바꾸는 등의 하부 수준 캐스팅(downcasting)을 위해 만들어진 연산자이다

- 이것의 적용 결과는 구현환경에 의존적이다. (이식성이 없다)

- 이런 캐스트는 하부 수준 코드 외에는 거의 없어야 한다.

static_cast

- 암시적 변환(비상수 객체를 상수 객체로 바꾸거나, int를 double로 바꾸는 등의 변환)을 강제로 진행할 때 사용한다

- 이루어진 타입 변환을 거꾸로 수행하는 용도(void*를 일반 타입의 포인터로 바꾸거나, 기본 클래스의 포인터를 파생 클래스의 포인터로 바꾸는 등)로도 쓰인다. 

- 상수 객체를 비상수 객체로 캐스팅하는 데 이것을 쓸 수는 없다(const_cast에서 사용한다)
  
  

구형 스타일의 캐스트보다 C++ 스타일의 캐스트를 사용하는 이유는 아래와 같다

- 코드를 읽을 때 알아보기 쉽다

- 캐스트를 사용한 목적을 더 좁혀서 지정하기 때문에 컴파일러 쪽에서 사용 에러를 전달할 수 있다
  
  

그 반대의 경우는 아래와 같은 경우일 때 추천한다 (무조건 더 좋다는 아니다. 화자의 추천이다.)

- 객체를 인자로 받는 함수에 객체를 넘기기 위해 명시호출 생성자를 호출하고 싶을 경우

 -> 이 방법은 캐스팅보다는 객체 생성의 의도를 주기 위함이다.



파생 클래스 객체에 대한 기본 클래스 포인터를 만드는(초기화하는), 흔한 코드이다. 그런데 두 포인터의 값이 같지 않을 때도 가끔 있다.

이런 경우가 되면 포인터의 변위(offset)를 자식 클래스 포인터에 적용하여 실제의 부모 클래스 포인터 값을 구하는 동작이 런타임(runtime)에 이루어진다.



객체의 메모리 배치구조를 결정하는 방법과 객체의 주소를 계산하는 방법은 컴파일마다 다르다. 



아래와 같은 코드에서는 캐스팅이 일어나면서 *this의 기본 클래스 부분에 대한 사본이 임시적으로 만들어지게 되는 것이지만 현재 기본 클래스의 부분이 아니다.

```
class Window{ // 기본 클래스
public:
	virtual void onResize() {...}; // 기본 클래스의 onResize 구현 결과
    ...
};

class SpecialWindow: public Window{ // 파생 클래스
public:
	virtual void onResize() // 파생 클래스의 onResize 구현 결과 *this를 Window로 캐스팅하고 그것에 대해 onResize를 호출한다. 
    {
    	static_cast<Window>(*this).onResize();
    	...
    }
	...
};
```

이 onResize가 임시 객체에서 호출된 것이다

SpecialWindow만의 동작을 현재 객체에 대해 수행하기도 전에 기본 클래스 부분의 사본에 대고 Window::onResize를 호출하는 것이다.

이 부분을 해결하기 위해서는 기본 클래스 버전을 호출하도록 하면 된다. 즉, 아래와 같이 코드를 짜면 된다.

```
class SpecialWindow: public Window{
public:
	virtual void onResize(){
    	Window::onResize(); // *this에서 Window:onResize를 호출한다.
        ...
    }
    ...
};
```



dynamic_cast 연산자가 쓰일 때 파생 클래스 객체임이 분명하고 파생 클래스의 함수를 호출하고 싶은데, 그 객체를 조작할 수 있는 수단으로 기본 클래스의 포인터(혹은 참조자)밖에 없는 경우가 있을 때 이 문제를 피하기 위해서는 아래와 같다

- 파생 클래스 객체에 대한 포인터(혹은 스마트 포인터)를 컨테이너에 담아둠으로써 각 객체를 기본 클래스 인터페이스를 통해 조작할 필요를 아예 없애버리는 것이다.

```
class Window {...};
class SpecialWindow: public Window{
public:
	void blink();
    ...
};

typedef std::vector<std::strl::shared_ptr<Window>> VPW;
VPW winPtrs;
...
for(VPW::iterator iter=winPtrs.begin(); iter!=winPtrs.end();++iter)
{
	if(SpecialWindow *psw = dynamic_cast<SpecialWindow*>(iter->get()))
    	psw->blink();
}
```

위와 같은 코드의 문제를 아래와 같이 해결하는 것이다



```
typedef std::vector<std::strl::shared_ptr<SpecialWindow>> VPSW;
VPSW winPtrs;
...
for(VPSW::iterator iter=winPtrs.begin(); iter!=winPtrs.end();++iter)
{
    	(*iter)->blink();
}
```

이 방법의 다른 문제는 존재하는데 Window에서 파생될 수 있는 모든 객체들에 대한 포인터를 똑같은 컨테이너에 저장할 수 없다. 



이를 해결하기 위해서는 원하는 조작을 가상 함수 집합으로 정리해서 기본 클래스에 넣어두면 된다.

```
class Window{
public:
	virtual void blink() {}
    ...
};

class SpecialWindow: public Window{
public:
	virtual void blink() {...}
    ...
};

typedef std::vector<std::trl::shared_ptr<Window>> VPW;
VPW winPtrs;
...
for(VPW::iterator iter=winPtrs.begin(); iter!=winPtrs.end(); ++iter)
	(*iter)->blink();
```



피해야 하는 또 다른 설계는 '폭포식(cascading) dynamic_cast'의 구조이다

```
class Window {...};
...
typedef std::vector<std::trl::shared_ptr<Window>> VPW;
VPW winPtrs;
...
for(VPW::iterator iter=winPtrs.begin(); iter!=winPtrs.end(); ++iter)
{
	if(SpecialWindow1 *psw1 = dynamic_cast<SpecialWindow1*>(iter->get())) {...}
    else if(SpecialWindow2 *psw2 = dynamic_cast<SpecialWindow2*>(iter->get())) {...}
    else if(SpecialWindow3 *psw3 = dynamic_cast<SpecialWindow3*>(iter->get())) {...}
}
```
